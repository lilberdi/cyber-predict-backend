# Отчёт по проекту для защиты

**Тема:** Разработка интеллектуальной системы прогнозирования результатов киберспортивных матчей (Counter-Strike 2)  
**Рабочее название:** Cyber Predict  
**Дисциплина:** Управление проектами  
**Команда:** 4 человека  
**Горизонт:** 12 недель (6 спринтов)  
**Дата отчёта:** 25 сентября 2026  
**Статус:** выполнен объём недель 1–4 и часть интеграционных работ (Swagger, живой календарь PandaScore)

**Дисклеймер.** Прогнозы учебные. Система не является букмекерским сервисом и не даёт финансовых рекомендаций.

---

## 1. Цель и постановка задачи

Создать воспроизводимый прототип, который:

1. берёт календарь предстоящих профессиональных матчей CS2 из **легального** источника;
2. оценивает вероятность победы одной из команд по **pre-match** признакам;
3. отдаёт результат через REST API и документирует его в Swagger;
4. сопровождается пакетом документов по управлению проектом.

Критерии успеха на полной защите курса (недели 11–12): живой прогноз на реальные upcoming, метрики модели, обоснованный отказ от HLTV, Docker-демо, устав / WBS / риски / RACI.

На текущей промежуточной защите уже можно показать пункты 1–4 в рабочем виде, без фронтенда и без XGBoost.

## 2. Управленческие решения (что говорить по дисциплине)

### 2.1. Ограничение объёма (scope)

Метод MoSCoW зафиксировал Must / Should / Won’t.

**Must (сделано или в работе):** календарь, вероятность, карточка матча, метрики модели, Docker, документы PM, легальные данные.

**Should (далее):** фильтры в UI, калибровка, XGBoost, переобучение по кнопке.

**Won’t (сознательно нет):** ставки, аккаунты, мобильное приложение, Dota/LoL, парсинг HLTV, live по раундам.

Это решение по управлению проектом: 4 человека и 12 недель не тянут «платформу уровня HLTV».

## 3. Правовое решение по данным (обязательный слайд)

**HLTV.org не используется.** Официального API нет. В Terms of Service (п. 2.2, с 27 января 2025) запрещены data mining, web scraping и создание похожего сервиса. Исторически HLTV предъявляла претензии неофициальным API.

**Чем заменили:**

| Контур | Источник | Зачем |
|---|---|---|
| История для обучения | Синтетический sample 480 матчей (знакомые названия CS2, исходы симулированы). Позже — licensed Kaggle/Hugging Face | Учить Elo и logreg без утечки и без scrape |
| Календарь upcoming | Официальный API PandaScore `GET /csgo/matches/upcoming` (`videogame_title=13`, CS2) | Живые ближайшие матчи |
| Фолбэк | `data/fixtures/upcoming.json` | Демо без интернета / без токена |

Двухконтурная схема — отдельное проектное решение: модель может жить на истории, а API календаря — на лицензируемом поставщике.

## 4. Архитектура и стек

**Решение:** публичный API на Go/Gin, обучение на Python, граница — только PostgreSQL. В запросе пользователя модель не вызывается (кроме отдельной задачи sync, которая пишет в БД).

```
PandaScore (раз в час или POST /jobs/sync-upcoming)
        ↓
   PostgreSQL (matches, teams, predictions)
        ↑
Python train / predict (Elo + logreg)
        ↓
   Go/Gin REST  →  Swagger / будущий frontend
```

| Слой | Технологии |
|---|---|
| API | Go, Gin, pgx, golang-migrate |
| ML | Python, pandas, scikit-learn, joblib |
| БД | PostgreSQL 16 |
| Демо | Docker Compose |
| Документация API | OpenAPI 3 + Swagger UI `/swagger/` |

Почему не нейросеть: табличные матчи лучше и дешевле предсказывает бустинг/логистическая регрессия. Почему не два HTTP-сервиса: меньше entropии на защите.

## 5. Что реализовано в продукте

### 5.1. REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Процесс жив, Postgres отвечает |
| GET | `/api/v1/matches/upcoming` | Ближайшие матчи + вложенный прогноз |
| GET | `/api/v1/matches/{id}` | Карточка матча |
| GET | `/api/v1/predictions/{id}` | Вероятность, confidence, топ-признаки |
| GET | `/api/v1/model/metrics` | Метрики обучения, дисклеймер, источники |
| GET/POST | `/api/v1/jobs/sync-upcoming` | Обновить календарь с PandaScore |
| GET | `/swagger/` | Интерактивная документация |

Контракт: `docs/openapi.yaml`. Эндпоинты разбиты по тегам: Служебные, Матчи, Прогнозы, Модель, Задачи.

### 5.2. Автообновление календаря

Консольная команда `python -m ml sync` больше не обязательна.

- Тикер в процессе API: `SYNC_INTERVAL=1h`.
- Ручной запуск: `GET/POST /api/v1/jobs/sync-upcoming`.
- Фильтр: не весь мусорный календарь, а матчи **топ-набора (~60 команд)** — seed известных оргов + топ по нашему Elo.
- По умолчанию `SYNC_REQUIRE_BOTH=false`: матч берётся, если **хотя бы одна** команда из топ-набора (например топ-30 против «топ-120»). Пара двух неизвестных ноунеймов отбрасывается.
- При `SYNC_REQUIRE_BOTH=true` нужны обе команды из набора; если таких пар нет, код смягчает фильтр, чтобы лента не была пустой.
- Успешный sync с PandaScore убирает старые fixture-матчи.
- Для новых пар пишется быстрый прогноз `elo_sync`. Полный logreg — `python -m ml predict`.

«Топ-60» — **не рейтинг HLTV**, а наш рабочий allow-list. Так мы не нарушаем ToS и не тянем все матчи третьего дивизиона.

### 5.3. Модель (baseline недели 3–4)

**Цель:** \(P(\text{победа team1})\) в серии BO1/BO3/BO5 как один исход. Фаворит при \(p \ge 0{,}5\).

**Критерии (только до даты матча):**

| Признак | Смысл |
|---|---|
| `elo_diff` | Разница Elo (старт 1500, K=32) |
| `form5_diff` | Разница винрейта за 5 матчей |
| `form10_diff` | То же за 10 матчей |
| `h2h_diff` | Личные встречи за 12 месяцев минус 0,5 |

Не используем счёт текущего матча, ADR, рейтинг после игры (утечка), карты veto.

**Как получается число:** StandardScaler → LogisticRegression → `p_team2 = 1 − p_team1`.  
**Confidence:** `|p−0,5| < 0,07` low; `< 0,15` medium; иначе high.

**Метрики на хронологическом тесте (384 / 96):**

| Метрика | Значение |
|---|---|
| Accuracy | ≈ 65,6% |
| Accuracy правила «всегда фаворит Elo» | ≈ 65,6% |
| Log-loss | ≈ 0,66 |
| Brier | ≈ 0,23 |

Для CS2 55–65% — нормальный baseline. Модель пока **не обгоняет** простое Elo; это честно сказано в отчёте. XGBoost запланирован на S3.

### 5.4. Почему предикты уже видны в Swagger

Это не «нейросеть в момент GET». Пайплайн уже один раз прогнан (sample → train → sync/predict) и/или API сам пишет `elo_sync` после hourly sync. Gin читает таблицу `predictions`.

Ограничение для защиты: сила команд на logreg выучена на **синтетической** истории с теми же названиями. Живой календарь уже с PandaScore; индустриальную точность мы не обещаем, пока не подставим licensed датасет.

## 6. Сценарий демонстрации (5–7 минут)

1. Открыть устав / этот отчёт (решения: HLTV нельзя, MoSCoW, два языка).
2. `docker compose up -d` (если ещё не запущено).
3. Открыть `http://localhost:<PORT>/swagger/`.
4. `GET /health` → `ok`.
5. `GET /api/v1/matches/upcoming` → `source: pandascore`, вероятности, `top_features`.
6. Разобрать один матч: Elo, форма, confidence.
7. `GET /api/v1/model/metrics` → accuracy 65,6% и сравнение с Elo-фаворитом.
8. `GET /api/v1/jobs/sync-upcoming` → `fetched / kept / dropped` (фильтр топ-60).
9. Если нет сети: сказать про fixtures и Docker.

Порт задаётся в `.env` (`PORT`). Токен PandaScore в `.env` **не показывать** и не коммитить.

## 9. Ответы на типичные вопросы преподавателя

**Почему не парсили HLTV?** ToS п. 2.2; риск претензий; учебный проект не должен строиться на запрещённом сборе.

**Откуда календарь?** PandaScore, раз в час или по эндпоинту. Без токена — fixtures.

**Почему уже есть проценты?** Офлайн train/predict и/или Elo после sync. Не live-нейросеть в GET.

**Почему 65%, а не 90%?** CS2 слабо предсказуем; 55–65% — норма. Мы сравниваем с baseline, а не обещаем «почти всегда».

**Что если топ играет с ноунеймом?** При текущих настройках матч **берём** (одна команда из топ-набора). Двух ноунеймов не берём.

**Где фронт?** Спринт S4. Сейчас контракт готов, UI можно делать по Swagger.

**Это ставки?** Нет. Дисклеймер в метриках и в отчёте.
