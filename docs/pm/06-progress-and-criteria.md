## 1. Что уже сделано

### Управление проектом

- Устав, реестр стейкхолдеров, матрица RACI, требования MoSCoW, WBS, спринт-план, реестр рисков.
- Статус-отчёт недели 4, устав в Word: `docs/pm/Plan_proekta_prognozirovanie_CS2.docx`.

### Backend (Go / Gin)

- REST API читает только PostgreSQL, модель в HTTP-запросе не вызывается.
- Эндпоинты:
  - `GET /health` — живость сервиса и связь с БД;
  - `GET /api/v1/matches/upcoming` — ближайшие и идущие матчи + вложенный прогноз;
  - `GET /api/v1/matches/{id}` — карточка матча;
  - `GET /api/v1/predictions/{id}` — вероятность, уверенность, топ-признаки;
  - `GET /api/v1/model/metrics` — метрики последнего обучения.
- Swagger UI: `/swagger/` (спека `/openapi.yaml`), разделы: Служебные, Матчи, Прогнозы, Модель.
- Docker Compose: `api` + Postgres, порт API из `.env` (`PORT`).

### Данные и модель (Python)

- История: 480 синтетических, но Elo-согласованных матчей знакомых команд CS2 (`python -m ml generate-sample` / `load-history`). Боевой licensed датасет можно подставить тем же CSV-форматом.
- Календарь upcoming: PandaScore (`GET /csgo/matches/upcoming`) или фикстуры `data/fixtures/upcoming.json`.
- Baseline: рейтинг Elo + логистическая регрессия.
- Признаки считаются только из прошлого (тест на отсутствие утечки post-match статы).
- Прогнозы записываются в таблицу `predictions` командой `python -m ml predict`.

### Качество baseline на тесте

Хронологический split 80/20: 384 матча обучение, 96 тест.

| Метрика | Значение | Смысл |
|---|---|---|
| Accuracy | ≈ 65,6% | Доля верных исходов |
| Elo-фаворит (без ML) | ≈ 65,6% | Всегда побеждает команда с большим Elo |
| Log-loss | ≈ 0,66 | Качество вероятностей (меньше — лучше) |
| Brier | ≈ 0,23 | То же для калибровки вероятности |

Для профессионального CS2 55–65% — нормальный уровень простого baseline. Модель пока не обгоняет правило «фаворит Elo»; это честный результат недели 4, не провал.

## 3. Почему в API уже есть предикты

Это не «нейросеть отвечает в момент открытия Swagger». Прогнозы **заранее посчитаны** офлайн-конвейером и лежат в PostgreSQL. Gin их только читает.

```
480 сыгранных матчей  →  ml train  →  Elo + файл elo_logreg.joblib
фикстуры / PandaScore →  ml sync   →  8 строк upcoming в matches
история + upcoming    →  ml predict →  таблица predictions
predictions           →  GET /api/v1/matches/upcoming
```

По шагам:

1. **История.** В базу загружены 480 завершённых матчей (sample). По ним считается сила команд.
2. **Обучение.** `python -m ml train` строит Elo и логистическую регрессию, пишет метрики в `model_metrics`.
3. **Календарь.** `python -m ml sync` добавляет предстоящие встречи (сейчас 8 штук из фикстур, если нет ключа PandaScore). Это реальные названия команд (Spirit, Vitality и т.д.), но расписание — демонстрационное, чтобы UI и Swagger не были пустыми.
4. **Прогноз.** `python -m ml predict` для каждой upcoming-пары берёт *текущие* Elo, форму и H2H **только из уже сыгранных матчей** и сохраняет `p_team1_win`.
5. **Показ.** Запрос `GET /matches/upcoming` джойнит `predictions`. Поэтому в Swagger сразу видны вероятности.

Итого: предикты есть, потому что контур недель 3–4 уже прогнан один раз. Это демонстрация архитектуры «модель пишет в БД, API читает», а не live-инференс и не букмекерская линия.

Чтобы обновить цифры после новых матчей: снова `sync` (календарь) и `predict` (пересчёт). Обучение (`train`) нужно, только если меняется история или сама модель.

## 4. По каким критериям считаются предикты

**Цель модели:** вероятность победы первой команды в матче (серия BO1/BO3/BO5 как один исход).  
**Кто фаворит в карточке:** `p_team1_win ≥ 0,5`.  
**Откуда признаки:** только матчи с датой *строго раньше* прогнозируемого (`played_at < scheduled_at`). Счёт и статистика *текущего* матча не используются.

### Таблица критериев (сейчас в коде)

| Признак | Что означает | Как считается | Зачем |
|---|---|---|---|
| `elo_diff` | Разница силы команд | Elo: старт 1500, K = 32; `R(team1) − R(team2)` | Долгосрочная сила по прошлым победам |
| `form5_diff` | Разница формы | Винрейт за последние 5 матчей team1 минус то же у team2 | Недавняя серия лучше/хуже среднего |
| `form10_diff` | Более длинная форма | То же за 10 матчей | Сглаживает случайные осечки |
| `h2h_diff` | Личные встречи | Доля побед team1 над team2 за 12 месяцев минус 0,5 | «Удобный» или «неудобный» соперник |

Не входят в текущий baseline (запланированы позже или сознательно исключены):

- счёт и карты текущего матча;
- ADR, K/D, рейтинг HLTV после игры (это утечка);
- veto карт, тир турнира, стабильность состава — спринт S3.

### Как из критериев получается число в API

1. Четыре признака масштабируются (`StandardScaler`).
2. Логистическая регрессия возвращает `P(победа team1)`.
3. `p_team2_win = 1 − p_team1_win`.
4. Уверенность `confidence` по отрыву от 50%:
   - `|p − 0,5| < 0,07` → `low` (почти монета);
   - `< 0,15` → `medium`;
   - иначе → `high`.
5. В `top_features` и `explanation` попадают вклад Elo, формы и H2H (в чью пользу признак).

Пример чтения карточки: если Spirit — team1, Vitality — team2 и `p_team1_win = 0,58`, модель оценивает Spirit выше на 58% **по накопленному Elo/форме/H2H из sample-истории**, а не потому что «так написано на HLTV».

### Ограничение, которое нужно проговорить на защите

Сейчас сила команд выучена на **синтетической** истории с теми же названиями, что в фикстурах. Поэтому предикт «Spirit фаворит» иллюстрирует пайплайн, а не претендует на индустриальный прогноз. После подключения licensed датасета и/или живого PandaScore те же критерии будут считаться по реальным прошлым матчам — код признаков менять не нужно.
